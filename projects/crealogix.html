The scaling problem

The same mobile system served institutions with different branding, capabilities, backend integrations and release schedules.

A change requested by one bank could affect the rest of the portfolio or add another permanent special case to the shared codebase. Each release had to account for security requirements, older integrations, bank-specific configuration and institutions moving at different speeds.

Representative institutions

The application portfolio included many Swiss cantonal and private banks, such as Zürcher Kantonalbank (ZKB), St.Galler Kantonalbank (SGKB), Aargauische Kantonalbank (AKB), Julius Baer and VZ.

Key architectural decision: variation through configuration

Institution-specific variation was expressed through configuration and modular composition rather than permanent branches in the shared code.

The reusable core provided common banking capabilities, while explicit boundaries isolated branding, backend integrations, security requirements and optional features. This allowed institutions to evolve at different speeds without turning every difference into platform-wide coupling.

Platform composition and security

Reusable core

Common capabilities remained shared while institution-specific behavior stayed behind defined extension points.

Optional capabilities

Features could be added or removed with a single configuration-line change.

Security constraints

Authentication, transaction signing and sensitive customer data placed strict constraints on platform composition and delivery.

Independent evolution

Each institution could move between backend versions and adopt capabilities on its own schedule.

Delivery infrastructure

The complete build and distribution process was automated and driven by configuration files specific to each institution.

Jenkins and Groovy scripts assembled, signed, hardened and delivered every application variant.

Automated assembly

Bank-specific configuration determined the modules, branding and backend environment included in every build.

Environment matrix

Each bank typically required 4–6 application variants for testing, internal use and different backend environments.

Signing and distribution

Some banks entrusted us with publication; others required ad-hoc signing, re-signing or delivery through institution-specific channels.

Application hardening

Every delivery passed through proprietary Promon tooling that obfuscated and protected the application before distribution.

Outcomes at portfolio scale

On average, the team released applications for 2–3 banks each week, with 4–6 application variants per institution.

When a substantial platform change required coordinated delivery across the complete portfolio, a release represented 100+ iOS builds and 200+ builds across iOS and Android. Every result was archived in our repository, then published or delivered through the path required by the institution.

Configuration-driven delivery and automation drastically reduced reported defects. Mobile delivery went from a recurring source of bugs and internal escalation to infrastructure that stakeholders expected to simply work.

Scope of ownership

My scope began with the mobile team's technical direction, architecture, code quality and delivery standards. It expanded into platform architecture: defining the reusable core, controlling extension points and evolving the configuration and delivery systems across the portfolio.

I also led interviews for incoming engineers and helped determine the skills the changing mobile team needed. Across my career I have conducted roughly 100 engineering interviews, shaping how I assess technical judgment, mentor engineers and communicate engineering standards.

Architectural lesson

The platform made the cumulative cost of configuration and extension points visible. A shortcut for one institution could become a permanent maintenance burden across the portfolio, so architectural decisions had to be judged partly by their operational cost over future releases.
