Case Study · eyeMaps

A map rendered from where you stand, not from above.

eyeMaps was an augmented-reality map requiring real-time 3D graphics, geographic data, terrain models, device sensors, offline storage, backend infrastructure and a cross-platform architecture.

The product idea and technical challenge

Traditional maps make the user mentally translate a top-down abstraction into the landscape around them. eyeMaps explored the inverse: render the map from the user's actual viewpoint.

The phone had to become an observer inside a live 3D geographic model while the user moved. Position, orientation, terrain and map features came from different data sources, coordinate systems and update rates.

Key architectural decision: Qt and a shared C++ core

Qt provided the cross-platform foundation needed to build for iOS and Android without maintaining two rendering engines. Performance-critical rendering and geographic-data layers lived in a shared C++ core, while device sensors, storage and other platform integrations remained native.

C++ and OpenGL provided the performance and low-level graphics control required to keep the 3D model synchronized at 60 fps. Qt supplied the cross-platform application architecture around that core.

Rendering, sensors and coordinate transformations

GPS established the observer's position; the accelerometer, gyroscope and magnetometer established viewing direction; digital elevation data formed the terrain; and OpenStreetMap supplied geographic features. The shared core transformed these inputs into a common local 3D coordinate system before rendering.

3D terrain

Elevation samples were transformed into a renderable landscape centered on the user's position.

Geospatial transforms

Real-world coordinates and OpenStreetMap features were mapped into the renderer's local coordinate system.

Device orientation

GPS, accelerometer, gyroscope and magnetometer data aligned the virtual viewpoint with the physical world.

Real-time rendering

OpenGL kept the native UI, virtual camera, terrain and geographic features synchronized as the user moved.

Backend architecture

Downloadable regions depended on three backend services that prepared their terrain, rendered map data and points of interest:

Terrain data

A terrain altimetry server processed NASA ICESat elevation data used to construct the 3D landscape.

Rendered maps

An OpenStreetMap tile-rendering server prepared the map imagery stored with each region.

Points of interest

An Overpass API server selected and delivered the geographic features required by the downloaded area.

Outcomes in the field

Users could download a region before trekking or riding through areas with unreliable coverage, including mountainous regions in Greece, Nepal and Switzerland, and continue using the map offline.

The native UI and real-time 3D model remained synchronized at 60 fps with sub-pixel precision across iOS and Android. Qt later profiled the project for its combination of Qt Quick, native UI and OpenGL.

Scope of ownership

As founder and principal engineer, I built the rendering engine, geographic and offline-data layers, mobile platform integrations and backend infrastructure. The work covered the complete path from raw terrain and OpenStreetMap data to the image rendered on the device.

Architectural lessons

Graphics, geographic data, sensors and UI behavior could not be designed independently: a small error in any one of them was immediately visible in the rendered landscape. The system required performance-sensitive code and precisely defined boundaries across two mobile platforms.
